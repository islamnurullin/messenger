# План разработки мессенджера «Messenger»

> Учебный проект: чат для веба, десктопа и мобильных — минимальный функционал как у Telegram
> (личные сообщения, группы, каналы). Сдача через GitHub с README и историей веток,
> с проверкой под нагрузкой (1000+ сообщений).

---

## 1. Что именно нужно сдать

| Требование из задания | Как закрываем | Критерий приёмки |
|---|---|---|
| Чат под веб-браузер | SvelteKit SPA | Регистрация, список чатов, переписка в реальном времени, поиск |
| Чат под мобильное приложение | Flutter (Android в приоритете) | Те же сценарии, что и в вебе, локальный кэш сообщений |
| Чат под десктоп | Electron-обёртка веб-сборки | Установка, системные уведомления, трей |
| Личные сообщения | `Chat.type = direct` | Переписка 1-на-1, статусы прочтения |
| Группы | `Chat.type = group` | Создание, участники, роли, инвайты |
| Каналы | `Chat.type = channel` | Подписка, публикация только админами, счётчик подписчиков |
| Демонстрация процесса | GitHub + README + ветки + PR + ADR | История коммитов и ревью читается как работа команды |
| Нагрузка 1000+ сообщений (поток) | Отдельный стенд и отчёт | p95 доставки < 500 мс при 200 соединениях, 0 потерь, 0 дублей |

**Вне скоупа** (сознательно, чтобы не расползся объём работ): звонки, секретные чаты, боты,
стикеры, голосовые сообщения, реакции. Если останется время — реакции и пересылка сообщений.

## 2. Стек и ключевые решения

| Слой | Технология | Решение / обоснование |
|---|---|---|
| Бэкенд | Django 5 + DRF | REST для CRUD и истории, вся бизнес-логика и права — здесь |
| Реалтайм | Centrifugo + `centrifuge-js` / `centrifuge` (Dart) | Не держим WS в Django: Centrifugo берёт на себя тысячи соединений |
| БД | PostgreSQL 16 | Источник истины, транзакционная нумерация сообщений |
| Поиск | Elasticsearch 8 | Полнотекстовый поиск, русский анализатор |
| Очереди/кэш | Redis 7 | Брокер Centrifugo, Celery, кэш счётчиков |
| Веб | SvelteKit + TypeScript | Основной клиент |
| Десктоп | Electron + electron-builder | Тонкая обёртка над веб-сборкой, а не третья кодовая база |
| Мобильный | Flutter (+ Android SDK) | Только Android; общий контракт REST/WS, локальный кэш |
| Инфраструктура | Docker Compose | Один `docker compose up` поднимает весь стек |
| CI | GitHub Actions | Линтеры, тесты, сборка — «процесс» для преподавателя виден в Actions |

**Главный архитектурный принцип:** Django — единственный источник правды. Клиенты не пишут
в Centrifugo напрямую «в обход»; сообщение сначала сохраняется в PostgreSQL, и только после
успешного коммита транзакции уходит в Centrifugo на рассылку.

### Зафиксированные решения (ответы заказчика)

| Вопрос | Ответ |
|---|---|
| Фронтенд-фреймворк | **Svelte** (Angular не используем) |
| Мобильная платформа | **Android** (iOS не собираем) |
| «1000+ смс» | **Поток** — упор на пропускную способность, а не объём истории |
| Деплой | **Пока локально** (`docker compose up`) |
| Аутентификация | **Логин + пароль** (телефон не используем) |
| Push-уведомления | **Пока нет** (только локальные при живом соединении) |

**Следствие для архитектуры:** раз проверяют поток, синхронная индексация в Elasticsearch
в горячем пути недопустима — только через Celery; пул соединений к PostgreSQL настраиваем
сразу, а не «когда упрёмся».

## 3. Архитектура

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│   Web    │  │ Desktop  │  │  Mobile  │
│ SvelteKit│  │ Electron │  │ Flutter  │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │ HTTPS REST  │             │
     │ WSS         │             │
     ▼             ▼             ▼
┌─────────────────────────────────────────┐
│            Centrifugo (WS-шлюз)         │
│   каналы: chat#<id>, user#<id>          │
└───────┬─────────────────────┬───────────┘
        │ HTTP API (publish)  │ connect/subscribe proxy
        ▼                     ▼
┌──────────────────┐   ┌──────────────┐
│  Django + DRF    │◄──┤    Redis     │
│  (источник истины)│   └──────────────┘
└───┬───┬──────┬───┘
    │   │      │
    ▼   ▼      ▼
┌────────┐ ┌──────────────┐ ┌────────┐
│Postgres│ │Elasticsearch │ │ Celery │
└────────┘ └──────────────┘ └────────┘
```

**Путь одного сообщения:**

1. Клиент → `POST /api/chats/{id}/messages` с `client_msg_id` (UUID, идемпотентность).
2. Django в транзакции: проверка членства и прав → выделение `seq` → запись в PostgreSQL.
3. `transaction.on_commit` → публикация `message.new` в Centrifugo (канал `chat#<id>`).
4. Centrifugo рассылает всем подписчикам, включая отправителя — один путь для всех.
5. Celery асинхронно индексирует сообщение в Elasticsearch.
6. Офлайн-получатели увидят сообщение при подключении — подтянут историю по `seq`.

## 4. Модель данных

```python
class User(AbstractBaseUser):
    id, username, display_name, avatar, last_seen_at, created_at

class Chat:
    id, type  # direct | group | channel
    title, avatar, created_by, created_at
    last_seq            # счётчик сообщений чата
    last_message_at

class ChatMember:
    chat_id, user_id, role  # owner | admin | member
    joined_at, last_read_seq, muted_until
    UNIQUE(chat_id, user_id)

class Message:
    id, chat_id, seq, sender_id
    type  # text | system | attachment
    text, reply_to_id
    client_msg_id        # UNIQUE(chat_id, client_msg_id) — защита от дублей
    edited_at, deleted_at, created_at
    UNIQUE(chat_id, seq)
```

**Индексы под нагрузку:** `(chat_id, seq DESC)` — история и пагинация;
`(chat_id, client_msg_id)` — идемпотентность; `(user_id, last_message_at DESC)` — список чатов.

**Почему `seq`, а не сортировка по `created_at`:** одинаковые timestamp при массовой вставке
дают нестабильный порядок и ломают пагинацию. Монотонный `seq` внутри чата решает это
и заодно даёт дешёвый расчёт непрочитанных: `unread = chat.last_seq - member.last_read_seq`.

## 5. Контракты

### REST (основное)

```
POST   /api/auth/register | login | refresh
GET    /api/me                     PATCH /api/me
GET    /api/chats                  POST /api/chats              # direct|group|channel
GET    /api/chats/{id}             PATCH /api/chats/{id}
GET    /api/chats/{id}/messages?before_seq=&limit=50
POST   /api/chats/{id}/messages
PATCH  /api/messages/{id}          DELETE /api/messages/{id}
POST   /api/chats/{id}/members     DELETE /api/chats/{id}/members/{uid}
POST   /api/chats/{id}/read        # {seq}
GET    /api/search/messages?q=&chat_id=
GET    /api/centrifugo/token       # JWT для подключения к WS
POST   /api/centrifugo/subscribe   # проверка права на канал
```

### События WebSocket

| Событие | Канал | Полезная нагрузка |
|---|---|---|
| `message.new` | `chat#<id>` | id, seq, sender, text, reply_to, created_at |
| `message.edited` / `message.deleted` | `chat#<id>` | id, seq, text / id |
| `typing` | `chat#<id>` | user_id, expires_in (эфемерное, без истории) |
| `read` | `chat#<id>` | user_id, seq |
| `chat.updated` / `member.added` / `member.removed` | `user#<id>` | chat_id, … |
| presence join/leave | `chat#<id>` | user_id |

Доступ к каналам проверяется на стороне Django (subscribe proxy), а не на клиенте —
иначе любой желающий подпишется на чужой чат.

## 8. Git-процесс — это часть оценки

- **Ветки:** `main` (защищена) ← `develop` ← `feature/<тема>`, `fix/<тема>`, `release/<версия>`.
- **Коммиты:** Conventional Commits (`feat(chats): …`, `fix(realtime): …`).
- **PR:** шаблон с «что сделано / как проверить / скриншот»; merge только через PR, не напрямую в `develop`.
- **README:** что за проект, mermaid-схема архитектуры, стек с обоснованием, `docker compose up` за 5 минут, скриншоты трёх клиентов, ссылка на отчёт по нагрузке.
- **`docs/adr/`:** 8–10 коротких ADR («почему Centrifugo, а не Channels», «почему seq, а не created_at», «почему Electron оборачивает веб»). Это то, что отличает курсовую от «накидал кода».
- **Issues + Milestones:** по одному milestone на этап — видно планирование.
- **CI:** pytest, `svelte-check`, `flutter analyze` на каждый PR.

## 9. Нагрузочное тестирование (поток, 1000+ сообщений)

Приоритет — **пропускная способность** (ответ заказчика: «поток»). Три сценария,
результаты пишем в `docs/load-test.md`:

1. **Поток (главный сценарий).** 200 одновременных WS-подключений, 1000 сообщений за прогон.
   Метрики: p95 «отправка → доставка всем» < 500 мс, 0 потерянных, 0 дублей,
   достигнутая пропускная способность (сообщений/с).
2. **Объём истории (вторичный).** 10 000 сообщений в одном чате → листание, подгрузка по 50.
   Метрика: p95 загрузки страницы < 150 мс, ≤ 100 DOM-узлов в зоне видимости.
3. **Устойчивость.** Разрыв соединения у 50 клиентов во время потока → recovery через
   историю Centrifugo без перезагрузки страницы.

Инструменты: k6/Locust для REST, `scripts/load_test.py` на asyncio для WS-протокола
Centrifugo. Дополнительно — `EXPLAIN ANALYZE` на горячих запросах, проверка отсутствия N+1
(`django-debug-toolbar`), мониторинг пула соединений к PostgreSQL.

## 10. Риски

| Риск | Смягчение |
|---|---|
| Три клиента — три UI, не хватит времени | Electron оборачивает веб; Flutter — минимальный паритет, не копия веба |
| Elasticsearch съедает RAM на ноутбуке | Отдельный compose-профиль: `docker compose --profile search up` |
| Centrifugo: рассинхрон версий и API | Зафиксировать версию в compose, свериться с документацией до этапа 5 |
| Flutter требует Android SDK (~3 ГБ) | Ставить только к этапу мобильного клиента, не раньше; запасной вариант — веб-демо в эмуляторе браузера |
| 1000+ сообщений «тормозят» в UI | Виртуальный список с самого начала, не «прикрутим потом» |
| Права доступа навыворот (подписка на чужой канал) | Subscribe proxy + тесты на доступ в pytest с этапа 5 |

## 12. Ближайший шаг

**Этап 1 закрыт.** Сделано и проверено: монорепо, `docker compose up` поднимает
Postgres/Redis/Centrifugo (Elasticsearch — профиль `search`), скелет Django с
`/api/health` (все проверки `ok`), скелет SvelteKit с работающими страницами «Обзор» и
«Состояние», CI, README, ADR, первый коммит в `main` и ветка `develop`.

**Этап 2 «Аккаунты» закрыт.** Сделано и проверено:

1. `apps/accounts`: `POST /api/auth/register`, `/login`, `/refresh`, `GET/PATCH /api/me`.
2. Валидация: уникальность `username` без учёта регистра (функциональный уникальный
   индекс `uniq_user_username_lower`), пароль через `AUTH_PASSWORD_VALIDATORS`,
   `username` нельзя изменить через `PATCH /api/me`.
3. Аватар: `PATCH /api/me` multipart, ограничение `ATTACHMENT_MAX_BYTES`, проверка
   формата через Pillow (JPEG/PNG/WebP), center-crop и ресайз до 256×256.
4. Тесты: 36 проходят (22 из них — API аккаунтов).
5. Фронтенд: `/login`, `/register`, `/profile`, автопродление `access` по 401,
   синхронизация вкладок через событие `messenger:auth`.
6. Демо: регистрация → вход → профиль работают вживую (проверено 12 сценариев).

**Этап 3 «Чаты» закрыт.** Сделано и проверено:

1. `apps/chats`: модели `Chat` (`type`, `title`, `direct_key`, `last_seq`) и
   `ChatMember` (`role`, `last_read_seq`), миграция `0001_initial`.
2. Идемпотентность личного чата — не проверкой в коде, а уникальным индексом
   `direct_key = "меньший_id:больший_id"`. У групп ключ `NULL`, поэтому уникальность
   на них не распространяется (`NULL` в Postgres не конфликтует сам с собой).
3. `POST /api/chats` (201 при создании, 200 если диалог уже был), `GET /api/chats`,
   `GET /api/chats/{id}`, `GET/POST /api/chats/{id}/members`,
   `POST /api/chats/{id}/read`.
4. Доступ: не-участник получает **404, а не 403** — 403 подтверждает существование
   чата, и перебором id можно узнать о чужих переписках.
5. unread = `last_seq - last_read_seq`, считается на сервере. Отметка о прочтении
   монотонна и клампится по `last_seq`: устаревший или завышенный seq от клиента
   не ломает счётчик.
6. Тесты: 62 проходят (26 новых). Отдельный тест держит стоимость списка чатов
   постоянной при росте числа чатов — иначе каждый чат добавлял бы 2–3 запроса.
7. Фронтенд: `/chats` (список, создание личного чата и группы, бейдж непрочитанных)
   и `/chats/[id]` (участники, добавление, автоотметка о прочтении).
8. Попутно исправлено в общем обработчике ошибок: `message` отдавал repr словаря
   DRF вместо строки для показа.

**Этап 4 «Сообщения» закрыт.** Сделано и проверено:

1. `apps/messaging`: модель `Message` (`seq`, `sender`, `body`, `client_msg_id`),
   ограничения `UNIQUE(chat_id, seq)` и `UNIQUE(chat_id, client_msg_id)`, миграция.
2. Номер `seq` выдаётся одной SQL-командой
   `UPDATE chats_chat SET last_seq = last_seq + 1 ... RETURNING last_seq`: Postgres
   блокирует строку чата до конца транзакции, поэтому два одновременных отправителя
   получают разные номера. Проверено 8 потоками × 5 сообщений — seq идёт 1..40 без дыр.
3. Идемпотентность отправки по `client_msg_id`: повтор возвращает 200 и то же
   сообщение, `last_seq` не двигается. При гонке `IntegrityError` откатывает всю
   транзакцию вместе с инкрементом, поэтому дыр в нумерации не остаётся.
4. `POST /api/chats/{id}/messages`, `GET /api/chats/{id}/messages?before=seq&limit=N`
   — курсор по `seq`, а не offset: offset съезжает, когда во время прокрутки приходит
   новое сообщение, и пользователь видит одну и ту же запись дважды. `has_more`
   определяется запросом `limit + 1` строк, без COUNT.
5. Публикация в Centrifugo через `transaction.on_commit`, одним пакетным запросом
   в `/api/batch` на канал чата и личные каналы всех участников.
6. Узкое место найдено живым замером: публикация занимала **2.4 с на сообщение**.
   Причина — `httpx.post` открывал новое TCP-соединение на каждый вызов (1.4 с на
   Windows) плюс отдельный запрос на каждого участника. После перехода на общий
   `httpx.Client` и пакетную рассылку — **46–92 мс**.
7. Тесты: 105 проходят (43 новых). Среди них тест на настоящую параллельность
   (8 потоков, `transaction=True`) — при замене `allocate_seq` на наивную версию
   `last_seq + 1` он падает, то есть действительно ловит гонку.
8. Фронтенд: лента с разделителями дней, отправка по Enter (Shift+Enter — перенос),
   автопрокрутка, подгрузка истории вверх с сохранением позиции чтения, дедупликация
   и вставка события по `seq` бинарным поиском (событие может прийти раньше ответа
   REST), индикатор обрыва связи.

**Этап 5 — «Realtime и надёжность».** План работ:

1. Догрузка пропущенного после обрыва связи: клиент запоминает последний `seq` и
   при переподключении спрашивает `GET /api/chats/{id}/messages?after=seq`.
2. Доставка через Redis Pub/Sub при нескольких воркерах: сейчас публикация идёт из
   процесса Django, при горизонтальном масштабировании каждый воркер публикует сам.
3. Presence («кто в сети») и статус «печатает…» через историю Centrifugo.
4. Метрики: `django-prometheus` — время ответа API, число сообщений в секунду,
   размер очереди публикации.
5. Нагрузочный сценарий из раздела 9: 1000+ сообщений потоком, замер p50/p95 и
   проверка, что счётчики непрочитанных не разъезжаются.
6. Фронтенд: виртуализация ленты при длинной истории, чтобы 10 000 сообщений не
   роняли прокрутку.
