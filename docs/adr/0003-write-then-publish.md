# 0003. Сначала запись в БД, потом публикация в Centrifugo

**Статус:** принято
**Дата:** 2026-10-22

## Контекст

Отправка сообщения затрагивает две системы: PostgreSQL (источник правды) и Centrifugo
(доставка подписчикам). Между ними нет распределённой транзакции, поэтому возможны
два порядка и оба дают сбой:

- **Сначала publish, потом insert.** Подписчики получают сообщение, которого нет в
  базе. Если вставка упадёт, клиент увидит фантом; при перезагрузке история его не
  покажет, и восстановить порядок будет нечем.
- **Сначала insert, потом publish без привязки к коммиту.** Если publish случится
  внутри транзакции, а транзакция откатится, подписчики получат сообщение, которого
  не существует.

## Решение

Публикация выполняется только после успешного коммита — через
`transaction.on_commit`:

```python
with transaction.atomic():
    message = Message.objects.create(...)
    chat.last_seq = message.seq
    chat.save(update_fields=["last_seq"])
    transaction.on_commit(lambda: publish_message.delay(message.pk))
```

`publish_message` — задача Celery: она читает сообщение из БД и вызывает HTTP API
Centrifugo (`POST /api/publish`) в канал `chat:<id>`.

Такой порядок даёт **at-least-once**: если публикация упадёт, Celery повторит её.
Дубликаты на клиенте отсекаются по `client_msg_id` — тому же UUID, который клиент
прислал при отправке.

## Почему через Celery, а не синхронно

Синхронный HTTP-вызов Centrifugo в обработчике запроса добавляет к времени ответа
сетевой круг (~5–20 мс) и делает отправку зависимой от доступности Centrifugo: если
он лежит, сообщения перестают сохраняться, хотя база жива. Через очередь отправка
сообщения не зависит от состояния доставки, а «поток 1000+ сообщений» не упирается в
синхронный вызов.

## Последствия

- Плюс: в БД не бывает сообщений, о которых никто не узнал, и наоборот.
- Плюс: падение Centrifugo не блокирует запись.
- Минус: доставка асинхронна — между коммитом и приходом сообщения подписчику есть
  задержка в десятки миллисекунд. Для мессенджера незаметно.
- Минус: клиент должен уметь догонять пропущенное. Это закрыто `seq` (см. ADR 0002) и
  `force_recovery` в конфиге Centrifugo: после реконнекта клиент просит восстановление
  истории и получает пропущенные сообщения из кэша Centrifugo, а при промахе — из REST.
