# ТЗ: что добавить к заданию

> Исходное задание короткое: «чат под веб, мобилку и десктоп, минимальный функционал как у
> Telegram, личные сообщения, группы и каналы; демонстрация через GitHub с README и ветками;
> проверка под нагрузкой 1000+ сообщений». Ниже — что в нём **не определено** и что предлагаю
> зафиксировать до первой строки кода.
>
> Пометки: **[БЛОКЕР]** — без ответа нельзя проектировать схему БД; **[MVP]** — берём в первую
> версию; **[ПОЗЖЕ]** — можно после сдачи; **[ОПЦИЯ]** — по желанию, если останется время.

## 2. Функционал: что фиксируем в MVP

### 2.1. Аккаунты **[БЛОКЕР — влияет на таблицу User]**

- [MVP] Регистрация по **username + пароль** (не телефон: нет SMS-провайдера).
- [MVP] Уникальный username, отображаемое имя, аватар, «о себе».
- [MVP] JWT: access (15 мин) + refresh (30 дней), refresh с ротацией.
- [MVP] Профиль: смена имени, аватара, пароля.
- [ПОЗЖЕ] Вход по email, восстановление пароля, 2FA.

> **Решение:** телефон не берём. Если преподаватель требует «как в Telegram» с номером —
> это отдельная интеграция (Twilio/SMS.ru) и дополнительный этап работ.

### 2.2. Личные сообщения **[MVP]**

- [MVP] Чат 1-на-1, создаётся при первом сообщении или явным действием.
- [MVP] Текст, ответ на сообщение (reply), редактирование, удаление «у себя»/«у всех».
- [MVP] Статусы: отправлено → доставлено → прочитано.
- [MVP] Индикатор «печатает…».
- [MVP] Непрочитанные: бейдж и разделитель «новые сообщения».
- [MVP] Online/offline (last seen).

### 2.3. Группы **[MVP]**

- [MVP] Создание, название, аватар, описание.
- [MVP] Роли: **owner / admin / member**. owner один, передаётся, админов несколько.
- [MVP] Добавление участников, кик, выход; инвайт-ссылка с TTL.
- [MVP] Системные сообщения («Иван добавил Марию», «Иван сменил название»).
- [MVP] Права: писать — всем; менять настройки и кикать — admin+.
- [ПОЗЖЕ] Закреплённое сообщение, упоминания @username, медленный режим.

### 2.4. Каналы **[MVP]**

- [MVP] Публичный канал: подписка по ссылке, публикация только admin+.
- [MVP] Роль подписчика: **reader** (читать) / admin (публиковать).
- [MVP] Счётчик подписчиков, список подписчиков для админа.
- [MVP] Приватный канал (вход по инвайту) — **[MVP]**, отличие только в доступе.
- [ПОЗЖЕ] Комментарии к постам (как в Telegram — привязанная группа обсуждения).

### 2.5. Сообщения и медиа

- [MVP] Текст, эмодзи (нативный ввод, без библиотеки стикеров).
- [MVP] Вложения: **изображения и файлы до 25 МБ**. Хранение — локальный диск (S3-совместимое
  хранилище — **[ОПЦИЯ]**).
- [MVP] Разбиение на страницы по 50, подгрузка вверх при скролле.
- [MVP] Идемпотентность отправки: `client_msg_id` (UUID) — повторная отправка не создаёт дубль.
- [ПОЗЖЕ] Голосовые, кружки, стикеры, GIF, опросы, геолокация.

### 2.6. Поиск **[MVP]**

- [MVP] Полнотекстовый поиск по сообщениям (Elasticsearch, русский анализатор).
- [MVP] Фильтры: по чату, по автору, по дате.
- [MVP] Поиск по названиям чатов и username.
- [ПОЗЖЕ] Поиск по файлам, подсветка совпадений, «перейти к сообщению» из результатов.

### 2.7. Уведомления

- [MVP] In-app: счётчики непрочитанных, звук (опция).
- [MVP] Desktop: системные уведомления (Electron `Notification`).
- [MVP] Mobile: **локальные** уведомления при живом соединении.
- [ПОЗЖЕ] **Push через FCM** — отдельная интеграция с Google, требует аккаунта и ключей.
  Это самая частая «дыра» в плане: без push мобильный чат не будит телефон в фоне.
- [MVP] Настройки: mute чата на 1ч/8ч/навсегда.

### 2.8. Присутствие и статусы

- [MVP] Online/offline по presence в Centrifugo.
- [MVP] Last seen («был(а) в 14:32»).
- [MVP] Печатает… с TTL 5 секунд.

## 3. Что я осознанно НЕ беру (и почему)

| Функция | Причина отказа |
|---|---|
| Голосовые/видеозвонки | WebRTC + TURN-сервер — это отдельный проект, не часть мессенджера |
| Секретные чаты (E2E) | Криптография на трёх клиентах, ключи, ротация — не влезает |
| Стикеры, GIF, боты | Требуют платформы/каталогов, к заданию не относятся |
| Платежи, премиум | Не про мессенджер для курсовой |
| Федерация (Matrix-подобная) | Архитектурно несовместимо с текущей моделью данных |

**Правило:** любая фича, которой нет в разделе 2, не делается без явного согласования.
Иначе проект расползётся и не будет сдан.

## 4. Нефункциональные требования

| Категория | Требование | Как проверяем |
|---|---|---|
| **Производительность** | p95 доставки сообщения < 500 мс при 200 соединениях | `scripts/load_test.py` |
| **История** | Чат с 10 000 сообщений: подгрузка страницы p95 < 150 мс | Locust + замер в браузере |
| **UI** | Плавный скролл 10 000 сообщений (виртуальный список, ≤ 100 DOM-узлов в зоне видимости) | DevTools Performance |
| **Надёжность** | 0 потерь и 0 дублей при разрыве соединения | Тест: kill WS у 50 клиентов |
| **Безопасность** | Доступ к каналу проверяется на сервере (subscribe proxy), не на клиенте | pytest на доступ |
| **Безопасность** | Пароли — Argon2; секреты — не в git; CORS-whitelist | Ревью + `git-secrets` в CI |
| **Готовность** | `docker compose up` поднимает всё с нуля за < 5 мин | Прогон на чистой машине |
| **Совместимость** | Chrome/Edge/Firefox последних версий; Android 8+ | Ручной чек-лист |
| **Доступность** | Клавиатурная навигация, контраст WCAG AA | Чек-лист (не полный аудит) |

## 5. «Демонстрация процесса» — расшифровка требования

Это самая нечёткая часть задания, и её легко провалить. Что именно делает процесс видимым:

- [MVP] **Ветки:** `main` (защищена, только через PR) ← `develop` ← `feature/*`, `fix/*`.
- [MVP] **PR на каждую фичу** с описанием «что / как проверить / скриншот», не менее одного
  ревью (можно собственного, но с содержательным комментарием).
- [MVP] **Conventional Commits** + осмысленные сообщения (не «fix», «update»).
- [MVP] **README** — вход в проект: что это, стек и почему, схема (mermaid), запуск за 5 минут,
  скриншоты трёх клиентов, ссылка на отчёт по нагрузке.
- [MVP] **ADR** (`docs/adr/`, 8–10 штук): «почему Centrifugo, а не Django Channels», «почему
  `seq`, а не `created_at`», «почему Electron оборачивает веб-сборку».
- [MVP] **Issues + Milestones** по этапам — видно планирование, а не импровизацию.
- [MVP] **CI (GitHub Actions):** pytest, `svelte-check`, `flutter analyze` на каждый PR.
- [ОПЦИЯ] **CHANGELOG.md**, теги версий `v0.1.0`…`v1.0.0`.

## 7. Ответы заказчика (зафиксировано)

| # | Вопрос | Ответ | Следствие для проекта |
|---|---|---|---|
| 1 | Angular или Svelte? | **Svelte** | Angular не используем вообще; админка — Django Admin |
| 2 | Мобильное: Android / iOS / обе? | **Android** | iOS не собираем, Flutter без iOS-специфики |
| 3 | «1000+ смс» — это что? | **Поток** | Меряем доставку под нагрузкой: много сообщений в секунду, а не объём истории |
| 4 | Нужен ли деплой? | **Пока локально** | CI собирает, но публичного стенда нет; всё через `docker compose up` |
| 5 | Телефон или логин+пароль? | **Логин + пароль** | `AbstractBaseUser` без `phone`; SMS-интеграции нет |
| 6 | Нужны ли push? | **Пока нет** | FCM вне скоупа; только локальные уведомления при живом соединении |

### Что меняется в плане из-за ответа №3 («поток»)

Приоритет нагрузочного теста смещается с объёма истории на **пропускную способность**:

- Главная метрика: **сколько сообщений в секунду держит система** и какой p95 доставки
  при заданном потоке (цель: 1000 сообщений за прогон, p95 < 500 мс, 200 соединений).
- Узкие места, которые надо готовить заранее: пул соединений к PostgreSQL
  (`CONN_MAX_AGE`, PgBouncer при необходимости), батчинг публикаций в Centrifugo,
  отсутствие синхронной индексации Elasticsearch в горячем пути (**обязательно Celery**).
- Объём истории (10 000 сообщений в чате) остаётся, но как **вторичный** сценарий:
  он проверяет UI-скролл и пагинацию, а не сервер.

## 9. Итог: что добавляется к исходному заданию

Короткий список дельты — всё это в исходнике не описано:

1. **Роли и права** (owner/admin/member/reader) — в исходнике «группы и каналы» без прав.
2. **Статусы доставки и прочтения** + непрочитанные + «печатает» + online/last seen.
3. **Вложения** (изображения/файлы до 25 МБ) — Telegram без медиа не бывает.
4. **Идемпотентность отправки** (`client_msg_id`) — иначе при обрыве будут дубли.
5. **In-app и desktop-уведомления**, настройки mute.
6. **Нефункциональные требования с числами** (p95, 10 000 сообщений, 0 потерь) — иначе
   «нагрузка 1000+» проверить нечем.
7. **Расшифровка «демонстрации процесса»** — ветки, PR, ADR, milestones, CI.
8. **Явный список того, что не делаем** — защита от расползания скоупа.
